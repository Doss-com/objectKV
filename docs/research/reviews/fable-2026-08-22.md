# Independent architecture review: objectKV / ZebraDB

Reviewed sources: the ZebraDB memo (`ZebraDB Object-Native Transaction Kernel...md`), the `okv` repository at commit `a0ec921` plus uncommitted work (README, `docs/BOOTSTRAP-PLAN.md`, `docs/EVALS.md`, `docs/DECISIONS.md`, `docs/POSTGRES-PATH.md`, `docs/CONTRIBUTOR-BOARD.md`, `program.md`, `rfcs/*`, `crates/okv-model`, `crates/okv-slate`, `crates/okv-eval`), and the external primary sources cited inline.

Conventions: claims with a link are sourced. Claims marked *Inference* are my judgment. `[EXISTS]` refers to code/docs actually in the repo today; everything else in the plan is `[PROPOSED]`.

What exists today, precisely: an in-memory single-threaded version-visibility model (point get/apply/replay, no scans, no range deletes), a SlateDB write-seam adapter pinned to git rev `e01619...` (externally assigned versions via `WriteOptions::seqnum`; versioned reads and scans explicitly not implemented, "blocked on a small upstream SlateDB API"), an eval runner with one smoke lane, and roughly 20x more planning prose than Rust. No WAL, no segments, no object-store conformance fixtures, no distribution, no benchmarks have run. The RFCs are question lists, not proposals.

---

## 1. Verdict and the three most dangerous assumptions

**Verdict:** The kernel thesis (FoundationDB-style transaction/storage separation with object storage as the permanent tier and a small replicated WAL as the fast tier) is sound and increasingly validated by production systems ([Neon](https://neon.com/docs/introduction/architecture-overview), [SlateDB](https://slatedb.io/blog/introducing-slatedb/), [Aurora DSQL](https://brooker.co.za/blog/2024/12/03/aurora-dsql.html)), but the plan systematically underprices the transaction-plane recovery problem and the semantic mismatch between the kernel's envelope and three of the four proposed serving layers, and the brief's serving fan-out (Redis, inverted search, PostgreSQL, HTAP) is scope inflation beyond even the memo's own non-goals.

**Dangerous assumption 1: that strict serializability is assemblable from parts, and the hard part is the happy path.** The memo's commit pipeline (sequencer, resolvers, Raft WAL) is the easy 20% of FoundationDB. FDB's actual moat is generation-based recovery: what happens when the sequencer, a resolver, and a log server fail in overlapping windows, and how the system proves no acknowledged commit is lost and no version is reused ([FDB SIGMOD '21 paper, section 2.4](https://www.foundationdb.org/files/fdb-paper.pdf); [recovery-internals design doc](https://github.com/apple/foundationdb/blob/main/design/recovery-internals.md)). FDB made this tractable only through deterministic simulation built *before* the database ([testing docs](https://apple.github.io/foundationdb/testing.html)). The memo names a `sim` crate but describes it as "deterministic-ish," and the phase plan does not gate WAL work on the simulator existing. *Inference:* "deterministic-ish" is worth approximately nothing; the value of simulation is exact replay of a failing seed, which is binary. This is the single most likely place the project dies.

**Dangerous assumption 2: that the serving layers fit the kernel's semantic envelope.** The kernel offers: read-version acquisition per transaction, OCC with abort-and-retry, low-single-digit-ms durable commits at best (Raft quorum fsync floor), bounded 5s transactions, and byte-opaque values. Redis users expect sub-millisecond per-op latency and per-command atomicity on rich data structures; PostgreSQL expects an 8 KB page substrate with its own WAL, MVCC, hint bits, and checkpointing; inverted search ingestion fans one document out into hundreds of term-key writes. Each layer either degrades visibly (Redis latency), duplicates the kernel (PG's second MVCC/WAL, acknowledged as the failure mode in the repo's own `BOOTSTRAP-PLAN.md` W8), or fights it (hot posting-list keys under OCC). The plan treats layers as pure consumers; in reality their requirements will leak back into kernel scope (TTL, push channels, atomic ops, schema awareness). Note also an internal inconsistency: the review brief's "distributed Redis semantics, distributed inverted search" appear nowhere in the memo or repo, and the brief's "swappable Parquet and Vortex physical formats" is stronger than the memo, which explicitly keeps Vortex out of the transactional path (memo section 30).

**Dangerous assumption 3: that "object storage is authoritative" plus async objectification makes the economics and the durability story safe.** Two sub-problems. (a) Durability: for the window `(O, C]` the authority is the 3-node Raft WAL, not object storage; if that cluster (likely one region, possibly one AZ each) is destroyed, acknowledged commits up to the objectification lag are gone. Neon handles this by putting Safekeepers across availability zones and stating the guarantee ([Neon architecture](https://neon.com/docs/introduction/architecture-overview), [safekeeper protocol](https://github.com/neondatabase/neon/blob/main/docs/safekeeper-protocol.md)); the memo's "the log makes writes fast, object storage makes it durable" marketing line contradicts its own invariant and no RPO is stated anywhere. (b) Economics: the memo's "tiny WAL" argument bounds the *durability tier's* size, not the object-request bill. S3 standard charges on the order of $5/million PUTs and $0.40/million GETs ([pricing](https://aws.amazon.com/s3/pricing/)) and throttles at roughly 3,500 writes / 5,500 reads per second per prefix ([performance guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)); objectification frequency, compaction rewrite bytes, and cold-read amplification are the real cost drivers, and Gate 1 as specified could pass on a friendly workload while the production shape (small values, high write rate, many ranges each flushing small segments) fails. WarpStream documented exactly this latency-for-request-cost trade for Kafka-on-S3 ([WarpStream](https://www.warpstream.com/blog/kafka-is-dead-long-live-kafka)).

## 2. The semantic contract that must be specified before implementation

The repo's RFC-0002/0003/0004 are currently lists of open questions. Outside experts cannot disagree with a question list; each of the following needs a written *position* with failure examples.

**Consistency and isolation.** Define the end-state claim (strict serializability) and, critically, the *interim* claims: phases S2 through S5 provide only monotonic versioned visibility per batch, not any transaction isolation; the README must say what each shipped milestone guarantees. Specify: whether read versions are causally fresh (external consistency) or may lag; read-your-writes inside a transaction (memo open question C, unresolved); snapshot-read staleness bounds when a worker's `applied_version < R`; follower/stale read modes if any; and the anomaly vocabulary used in evals (adopt [Elle's](https://github.com/jepsen-io/elle) model, [paper](https://arxiv.org/abs/2003.10554)).

**Durability and acknowledgement.** Define exactly what COMMITTED means: quorum-fsynced in the WAL, single region. State the RPO if the WAL cluster is lost (up to objectification lag; the memo's own example is 30 s). Specify `commit_unknown` semantics and the idempotency mechanism clients must use (FDB's pattern: [known limitations](https://apple.github.io/foundationdb/known-limitations.html)). Specify behavior when objectification stalls: WAL growth bound, then commit throttling (ratekeeper on `C - O`), then refusal; never silent unbounded growth.

**Time and version model.** `Version(u64)` exists; unspecified: epoch/generation encoding so versions cannot be reused across recovery; whether version gaps are legal and how recovery distinguishes a gap from a lost log suffix (RFC-0002 open question); the version-to-wall-clock mapping needed for PITR and for the OLAP watermark; maximum version allocation rate; versionstamp exposure in keys.

**Range ownership.** Who assigns generations, where the range map durably lives, lease versus fencing-token semantics, routing-cache staleness handling (client retries on `wrong_generation`), split/merge concurrency with in-flight transactions and with the resolver's conflict windows.

**Failures and fencing.** The critical rule: fencing must be enforced at the *publication point* (manifest CAS carries the generation), not by asking stale nodes to stop. Enumerate: sequencer failover, resolver state loss (adopt FDB's answer: recovery to a new generation aborts in-flight transactions), zombie compactors, zombie materializers, and double-application by a worker (the `okv-slate` replay fingerprint is the right instinct).

**Recovery.** Generation-based recovery protocol with an explicit RTO target; the reconciliation order between WAL tail, range manifests, and the global watermark; and, unsolved in the memo: the bootstrap circularity. Memo section 14 puts manifest authority "inside the transaction/control system," but the transaction system's own metadata must live somewhere that exists before the database does. FDB uses coordinators plus a system keyspace; Neon uses a control plane. This needs a decision (see section 10).

**GC.** Reachability roots enumerated (manifests, snapshots, branches, backups, active read versions, CDC positions, analytical snapshots); the safety horizon's interaction with long-lived read versions and slow CDC consumers (a stuck consumer must not pin GC forever without an explicit policy); LIST as leak-audit only (repo already states this correctly); delete batching and its own request cost.

**Backup and restore.** Snapshot-as-metadata-root is not backup: it does not survive bucket deletion, account compromise, or a bad GC bug. Specify cross-bucket/cross-account replication of segments plus out-of-band metadata export, restore rehearsal cadence, and the PITR window as a first-class retention setting.

**Multi-tenancy.** Keyspace-prefix tenancy versus cell-per-tenant; noisy-neighbor policy in the shared sequencer/WAL (per-tenant ratekeeping); tenant deletion (range-clear plus compaction, or crypto-shredding); per-tenant encryption keys and whether segments may mix tenants (this constrains compaction).

**Object-store semantics.** Define a required-semantics floor and conformance-gate it (repo task T4 is right). Floor should be: strong read-after-write for named objects (S3 has been strongly consistent since Dec 2020: [consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)); conditional PUT with `If-None-Match`/`If-Match` (S3 since 2024: [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html); GCS [generation preconditions](https://cloud.google.com/storage/docs/request-preconditions); Azure [ETags/leases](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage)); range GET; multipart. Explicitly note there is no atomic rename and no multi-object atomicity. "S3-compatible" third parties vary on conditional ops; support is a conformance-test result, never a category claim.

**Observability.** `C`, `O`, per-worker applied version, WAL size, and objectification lag as first-class gauges; per-operation object-request and byte accounting (cost is a metric, not an afterthought); manifest-transition audit log; and cardinality budgets from day one (see section 8).

## 3. FoundationDB patterns: what transfers, what changes

**Transfers cleanly** (all per the [FDB paper](https://www.foundationdb.org/files/fdb-paper.pdf) and [architecture docs](https://apple.github.io/foundationdb/architecture.html)):

- Read-version / commit-version separation, versionstamps, and the OCC resolver model with explicit read/write conflict ranges. Resolver state is only the recent write window, independent of data location, so it is indifferent to where bytes live.
- Transaction size/lifetime limits (5 s, 10 MB) and the client retry loop with `commit_unknown` ([known limitations](https://apple.github.io/foundationdb/known-limitations.html)).
- Generation-based recovery *as a concept*: fence the old transaction system, recover the log, start a new generation, abort in-flight transactions.
- Ratekeeper as the mechanism that converts lag into commit backpressure.
- Unbundled stateless roles and the deterministic-simulation philosophy.
- Tagged mutation streams (log routes mutations to interested consumers).

**Changes or fails on object storage:**

- **Log popping becomes the system's central risk.** In FDB, tLogs discard a mutation once storage servers have made it durable locally, a fast local loop. Here, popping depends on objectification across *all* affected ranges (the memo's conservative `O = min(range watermark)` is correct but couples WAL retention to the slowest range and to object-store health). An S3 brownout stalls popping and grows the WAL; FDB never had this failure mode. *Inference:* WAL overflow policy (spill, throttle, refuse) is a required design, not an optimization.
- **`applied_version >= R` waits change character.** FDB storage servers hold all their data locally, so waiting for a version is milliseconds. A cold or freshly assigned serving worker here may need manifest loads and object GETs before it can serve `R` at all; read-version freshness guarantees must be restated with explicit staleness/timeout behavior.
- **MVCC window inversion, in the kernel's favor.** FDB keeps ~5 s of versions in storage-server memory; here immutable versioned segments make deep history and time travel nearly free. Snapshots, branches, and PITR genuinely transfer *better* than FDB.
- **Shard movement transfers better.** FDB moves data by copying between storage servers; here it is a metadata operation (memo section 22). This is the strongest genuinely novel claim and should be the headline benchmark.
- **Storage-server durability role disappears, but its serving role does not.** The memo sometimes talks as if workers are "just cache"; they are also the apply pipeline that must deterministically produce identical segments from the mutation stream, or replicas diverge. That determinism requirement (same sort, same tombstone handling, same segment boundaries or content-addressing tolerance for differing boundaries) is unspecified.
- **One correction to the brief's premise:** the big three object stores are no longer eventually consistent for single-object read-after-write (S3 strong since 2020; GCS and Azure similar). The real adversaries are latency variance, 503 throttling per prefix, request pricing, lack of multi-object atomicity, and the semantic spread of "S3-compatible" stores. Design and test for those, not for 2019-era S3.

Two concrete code-level findings supporting the kernel rows, both *inference from reading the pinned code*: (1) `okv-slate`'s `apply` has a TOCTOU between the `latest_version()` monotonicity check and the write; two concurrent appliers with different versions can interleave so a lower version lands after a higher one unless SlateDB itself rejects non-monotonic seqnums, which the adapter does not verify. (2) `latest_version()` returns SlateDB's internal snapshot seq, silently equating SlateDB's sequence space with okv commit versions; any upstream-internal write that consumes a seqnum breaks the equation. Both confirm the memo's own suspicion that SlateDB's writer-owned sequencing is the first seam to fail (memo section 35).

## 5. Are swappable Parquet/Vortex formats a sound kernel boundary?

**Split the question in two; the plan conflates them.**

**(a) OLTP kernel segments: yes, a narrow trait is sound, but it is bigger than the memo's `VersionedSegment`.** The workable contract is a *logical versioned-record* contract, not a file-format contract:

- Read side: `get(key, version)`, `scan(range, version, direction)`, key bounds, version bounds.
- Build side: consume a sorted `(user_key, version, kind, value)` stream; report resulting refs.
- Identity: checksum, `format_version`, size, entry counts.
- Evidence capability discovery: bloom filter present, zone maps present, so the planner can price reads (Vortex's "evidence/layout" vocabulary is the right shape here: [vortex.dev](https://vortex.dev/)).
- Cost hints: preferred range-GET alignment and footer/index read pattern, because a Parquet-style footer costs an extra GET on cold open while formats designed for object storage minimize round trips.

**Where format-specific semantics leak, in order of severity:**

1. **MVCC entry kinds.** Tombstones, range deletes, and merge/atomic operands are *kernel* semantics every format must encode identically. Parquet and Vortex have no native tombstone or merge concept. Either the kernel resolves merges before segment build (losing merge-operator laziness) or every format implements the merge algebra, which means it is not "swappable," it is "reimplemented." Range deletes are the worst offender; the memo correctly flags them (section 10) but the segment trait as sketched cannot express them.
2. **Compaction planning.** Split-point selection, output size estimation, and rewrite cost depend on format internals (row groups, block sizes, encodings). The compactor cannot be format-agnostic; it needs a format-provided cost model. Keep the compaction *protocol* (immutable in, CAS publish, crash-safe garbage) in the kernel and the *planner* behind the format trait.
3. **Value opacity.** The kernel is byte-opaque. Columnar formats only pay off if values are structured. The moment "swap Vortex into the OLTP segment" implies predicate/projection pushdown, schema awareness has leaked into the kernel. The memo actually gets this right (section 30: Parquet stays a *derived* artifact produced by the record layer's materializer); the review brief's framing ("swappable physical file formats such as Parquet") is not sound at the kernel layer and should be corrected in public copy.
4. **Cache granularity and encryption.** Block-aligned caching, checksum scope, and per-tenant encryption boundaries differ per format and constrain the NVMe cache design.

**(b) OLAP artifacts: yes, cleanly swappable, behind the materializer, not the kernel.** Parquet first, Vortex as a later experiment, exactly as the memo says. Vortex's claimed advantages (fast random access, extensible layouts, [LF incubation](https://www.linuxfoundation.org/press/lf-ai-data-foundation-hosts-vortex-project-to-power-high-performance-data-access-for-ai-and-analytics), [repo](https://github.com/vortex-data/vortex)) are real but its role as a unified OLTP+OLAP segment is a research bet; the memo's own "performance decides, not architecture aesthetics" is the right posture.

*Inference summary:* one trait is a lie; use two. `SegmentReader`/`SegmentBuilder` for kernel OLTP segments with kernel-owned MVCC algebra, and a separate `AnalyticalArtifact` contract owned by the record/materializer layer. The narrow waist is the sorted versioned-entry stream plus the publication protocol, not "a file format."

## 7. Ten falsifiable experiments

Each: invariant / workload or fault / metric / gate / decision resolved. Gates marked (declare) need a number committed in the suite TOML before running, per the repo's own anti-gaming rules.

1. **Cold point-read amplification.** Invariant: correct value at requested version. Workload: 10 GiB dataset, cache deleted, uniform random point reads. Metric: remote GETs and bytes per read; p50/p99/p999 latency. Gate: <= 2 GETs per read, p99 <= (declare) ms. Resolves: SST/metadata layout and eager-metadata set; Gate 1 core.
2. **Hot-path ceiling.** Invariant: zero remote GETs after warmup. Workload: Zipf reads, fixed RAM/NVMe budget. Metric: ops/s, p99. Gate: p99 < 10 ms per memo target. Resolves: whether the cache hierarchy suffices without a regional cache tier.
3. **Durable commit latency and loss-freedom.** Invariant: every acknowledged commit survives. Workload: 3-node Raft WAL, mixed commit sizes, with repeated leader kill/restart and disk-full on one follower. Metric: commit p50/p99, election-window p99, acked-loss count. Gate: zero loss; p50 < 10 ms, p99 < 25 ms (memo targets). Resolves: WAL v1 (raft-rs, one log group) adequacy; Gate 2.
4. **Objectification under object-store brownout.** Invariant: no acked loss; system throttles predictably rather than failing chaotically. Fault: 30 min of injected 503s/10x latency on PUTs. Metric: `C - O` lag, WAL size curve, commit-rate response, recovery time after fault clears. Gate: WAL bounded by declared policy; full watermark recovery < (declare) min. Resolves: ratekeeper-on-lag design and WAL sizing; the memo's biggest unstated failure mode.
5. **Cost and request curves.** Invariant: correctness unchanged. Workload: fixed 24 h OLTP shape (1 KiB values, declared write/read rates, Zipf) on S3, S3 Express, and MinIO. Metric: $/hour decomposed into PUT, GET, storage; object bytes written per logical byte ingested (compaction write amp); requests/s per prefix vs throttle limits. Gate: total cost within (declare)x of a triple-replicated NVMe baseline. Resolves: the economics thesis itself, plus tiered-vs-leveled compaction choice; Gate 1's teeth.
6. **Empty-cache takeover.** Invariant: no incorrect read ever served. Fault: kill a serving worker; start a replacement with empty disk at 1/10/100 GiB dataset sizes. Metric: time-to-first-correct-read as a function of dataset size; bytes copied. Gate: flat curve (size-independent), zero bulk copy. Resolves: disposable serving; Gate 3, the "Neon inversion" claim.
7. **Serializability under contention.** Invariant: every generated history passes the reference model and Elle. Workload: generated concurrent transactions at 1/10/50% hot-key overlap. Metric: anomaly count, abort rate, goodput vs contention. Gate: zero anomalies; abort/goodput curve published. Resolves: OCC viability for target workloads and ordered-vs-hashed resolver domains; Gate 5.
8. **Metadata-only split/move under load.** Invariant: zero impossible reads, no acked loss, stale-generation publications rejected. Fault: split and move a hot range during sustained writes, with the old owner deliberately kept alive and publishing. Metric: durable bytes copied, cutover p99, rejected-stale-publication count. Gate: bytes ~ metadata only; cutover < (declare) s. Resolves: fencing-at-publication design; Gate 4.
9. **GC vs snapshot/branch race.** Invariant: no reachable object is ever deleted. Fault: continuous branch/snapshot creation racing GC cycles, plus injected slow manifest reads. Metric: premature-delete count (verified by full read of all branches afterward), leaked bytes over time. Gate: zero premature deletes; leak growth bounded and audited via LIST. Resolves: reachability protocol and safety horizon.
10. **Serving-envelope probe (Redis).** Invariant: RESP GET/SET/INCR results linearizable per key (checked with Porcupine). Workload: thin RESP frontend over the kernel; hot-key INCR via kernel atomic op vs via OCC transaction; comparison run against Redis and published MemoryDB figures. Metric: p50/p99 per op, hot-key throughput, abort rate. Gate: (declare) honest targets, e.g. p99 < 5 ms. Resolves: whether the Redis lane is a product or a demo, and whether atomic mutations must be in kernel v1 rather than deferred.

## 8. Robustness plan

**Deterministic simulation, first, not alongside.** The memo's trait seams (`Clock`, `Network`, `DurableLog`, `ObjectStore`, `Random`) are correct; the ordering is not. Build the simulator before the WAL crate and make "runs under sim" a merge requirement for every distributed component. Use [madsim](https://github.com/madsim-rs/madsim) or [turmoil](https://github.com/tokio-rs/turmoil) rather than a homegrown "deterministic-ish" harness; determinism must be exact (single logical thread, seeded RNG, virtual time) so any failure reproduces from a seed, which is the entire point of [FDB's approach](https://apple.github.io/foundationdb/testing.html). Add buggify-style fault amplification. Consider [Antithesis](https://antithesis.com) for whole-binary exploration once a multi-process build exists.

**Isolation checking.** Two oracles: the existing `okv-model` for versioned visibility (extend with scans and range deletes before anything else consumes them), and [Elle](https://github.com/jepsen-io/elle) over register and list-append workloads for transactional histories once OCC exists. [Porcupine](https://github.com/anishathalye/porcupine) for the linearizable single-op surfaces (Redis probe, admin ops). Run [Hermitage](https://github.com/ept/hermitage)-style anomaly tests as documentation of the claimed isolation level.

**Crash and fault injection.** The memo's scenario list (section 36) is good; make it the E4 suite verbatim. Ensure both "lost success response" variants exist: WAL append acked but response dropped, and object PUT succeeded but response dropped, since both drive the idempotency design (the `okv-slate` commit-fingerprint mechanism must be tested under exactly this fault).

**Object-store emulation.** Build one fault-injecting `ObjectStore` wrapper used by every test: latency distributions with heavy tails, per-prefix 503 throttling, lost-success responses, conditional-op conflicts, stale LIST, and per-operation request/byte/cost accounting so cost regressions fail tests, not invoices. Run the conformance suite (repo task T4) against memory, filesystem, MinIO, and one real S3 + GCS profile; publish results as a support matrix, since conditional-write behavior is the axis where "S3-compatible" stores diverge.

**Long-running suites.** A weekly soak: continuous writes, compaction, GC, branch churn, snapshot creation, worker kills, and clock skew, with invariant checks (no impossible read, no premature delete, watermark monotonicity) evaluated continuously. Quarterly disaster drill: destroy the WAL cluster, restore from object storage alone, measure and publish the achieved RPO against the stated one.

**OTel cardinality and cost.** The eval suite already mandates OTLP signals; unmanaged, this will distort the benchmarks it instruments and blow up cost as ranges multiply. Rules: metric allowlist; no per-key or per-transaction labels ever; per-range labels capped with overflow into an "other" series per the [OTel cardinality-limit spec](https://opentelemetry.io/docs/specs/otel/metrics/sdk/); traces sampled, never 100%, in perf lanes; a declared monthly telemetry budget treated like any other eval budget.

## 9. Phase order to get outside experts contributing quickly

The current plan's contributor surface is documentation-heavy and code-light, and its RFCs are question lists. Credible database people contribute where there is a runnable core, a crisp invariant, and a reviewable position to attack. Reorder as follows:

1. **Publish the honest now-shape** (model, eval chassis, SlateDB adapter, `[EXISTS]/[PROPOSED]` labeling, which is genuinely good and rare; keep it). Do not publish any Redis, search, or PostgreSQL claim; the brief's "distributed PostgreSQL" phrasing must never appear in public copy, and the repo's own D5 supports this.
2. **Rewrite RFC-0002/0003/0004 as positions with worked failure examples**, not question lists, and invite external review on them explicitly. This is the highest-leverage expert magnet: distributed-systems reviewers will engage with a version-model spec they can find holes in.
3. **Ship the Gate 1 baseline lanes (T4, T5, T6)** and solicit benchmark reproductions on other hardware/backends. Benchmark receipts are the ideal first-contribution: bounded, valuable, no architectural trust required.
4. **Differential fuzzing (T2)** next; property-testing contributors are abundant and the oracle already exists.
5. **Simulation harness before the WAL**, then the WAL and Gate 2 inside it. Recovery-protocol review is where you want the FDB/Raft-literate experts, and they will only show up if failures reproduce from seeds.
6. **Disposable serving (Gate 3), then ranges/fencing/OCC (Gates 4-5)**, each with its eval lane opened as a contributor surface.
7. **Layer experiments live in separate repos consuming only the public API**: a RESP demo (experiment 10) and a Tantivy-catalog demo. Framed as demos over the kernel, they attract layer-specialist contributors without contaminating kernel scope, and they exercise the API as a real consumer, which is the FDB Record Layer lesson ([paper](https://www.foundationdb.org/files/record-layer-paper.pdf)).
8. **PostgreSQL remains a research doc plus the read-only surface spike (T7)** until Gate 2 passes; then a Neon-shaped smgr bridge prototype, publicly labeled "PostgreSQL storage bridge research."
9. **HTAP materialization** only after the ZebraDB record layer exists to give values structure.

## 10. Decisions now, decisions to keep reversible, and a pre-mortem

**Decide now (these harden into persisted state or public contract):**

1. **Version model** (RFC-0002 as a position): epoch encoding, gap legality, replay contract, version-to-timestamp mapping. Everything downstream serializes it.
2. **Object-store semantics floor**: conditional PUT and strong read-after-write are required; "compatible" is a conformance-test outcome. This decides what "S3-compatible" means in every public claim.
3. **Where control-plane metadata authority lives** (range map, epochs, watermarks): a small dedicated consensus service versus in-kernel system keyspace, and how it bootstraps. The memo's circularity here is unresolved and blocks W3-W5.
4. **Acknowledgement and RPO contract**: what COMMITTED means, `commit_unknown` semantics, and the stated data-loss window if the WAL cluster is destroyed, including WAL replica placement (multi-AZ minimum).
5. **Public claim policy and OSS boundary**: Apache-2.0, embedded-first wedge, kernel-not-ZebraDB, and a rule that no serving-layer noun (Redis, PostgreSQL, search) appears in public material before its gate passes.

**Keep reversible (hide behind traits, defer with evidence):**

1. Compaction strategy (tiered vs leveled vs hybrid); experiment 5 decides.
2. SlateDB reuse depth (adapter vs fork vs extraction); the adapter's seqnum coupling already shows where it will break, so keep the segment trait sovereign.
3. Raft implementation (raft-rs vs OpenRaft) behind `wal-api`.
4. Resolver partitioning (ordered ranges vs hash domains); experiment 7 decides.
5. Transport (gRPC vs framed), content addressing, and Parquet-vs-Vortex for analytical artifacts.

**Pre-mortem: it is early 2028 and the project failed. Ranked causes and tripwires:**

1. **Recovery swamp.** The team built the happy-path transaction plane, then spent a year chasing generation-recovery and watermark bugs because simulation came late. Tripwire: any WAL/recovery code merged that cannot run under the deterministic harness.
2. **Economics passed the demo, failed the shape.** Gate 1 passed on 10 GiB with friendly value sizes; production-shaped workloads (small values, many ranges, high churn) drowned in PUT costs and compaction rewrite. Tripwire: experiment 5's cost decomposition regressing quarter over quarter, or Gate 1 passing without a small-value high-range-count profile.
3. **Serving fan-out diluted the team and burned credibility.** A "distributed Redis" demo benchmarked 30x slower than Redis went viral for the wrong reason; experts wrote the whole project off. Tripwire: any layer work started before its envelope probe published honest numbers.
4. **SlateDB drift.** Upstream moved, the pinned fork calcified, and single-writer manifest assumptions leaked into okv's metadata design. Tripwire: the T3 seam inventory not maintained per upstream release; kernel code importing SlateDB types outside `okv-slate`.
5. **ZebraDB gravity.** DOSS delivery pressure pulled product shortcuts into the kernel, and the OSS boundary (D2) became fiction; no external adopter ever materialized. Tripwire: any kernel PR justified primarily by a ZebraDB deadline.
6. **Doc-ware repulsion.** The repository stayed 20:1 prose-to-code for two more quarters and the intended expert contributors never engaged. Tripwire: contributor-board tasks T2/T4/T5/T6 still open 90 days after publication.

The plan's strongest assets are real: the gate discipline, the anti-gaming eval design, the claim-labeling honesty, and the choice to prove physical economics before building distribution. The correction it needs is symmetry: apply that same discipline to the transaction plane's recovery story, the serving layers' semantic envelopes, and the durability claim's fine print, before any of them appear in a sentence with "distributed."
