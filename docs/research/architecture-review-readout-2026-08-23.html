[01]Strategy thesis

The concept is coherent only if authority, recovery, permanent bytes, serving, and analytical truth remain separate but compose exactly.

01
Bounded cell authority
FDB-like ordered transactions inside one tenant domain.
02
Replicated WAL suffix
Fast commit authority for versions not yet objectified.
03
Immutable bulk state
Fenced publication into object-native permanent storage.
04
Disposable serving
RAM and NVMe cache, reconstructable from durable closure.
05
Exact HTAP at T
Columnar base plus durable live tail through one version.

[02]Strategy status

Cell transaction semantics

Exists

Actual-read witnesses, range phantoms, causal versions, partitioned resolvers, ordered commit proxies, and online range split contracts.

Boundary: no independent-host or end-to-end capacity envelope.

Durability and recovery

Exists

Authenticated tLog inventories, generation replacement, staged takeover, absence-quorum abort, retained outcomes, and fresh serving.

Boundary: topology and inventory work remain locally bounded only.

Object-native physical tier

Exists

Immutable publication, fenced root authority, fresh reopen, SlateDB profile, compaction work, and MinIO protocol fixture.

Boundary: GCS economics, throttling, brownout, and multi-host durability.

Resolver hotspot scaling

Active work

Balanced diagnostic passed semantic gates and measured a 3.814 median split/source throughput ratio.

Boundary: clean full curve and five negative controls are pending.

Exact HTAP overlay

Exists

DataFusion merges Parquet base and ordered Arrow tail to an exact target version.

Boundary: durable manifests, leases, interval reads, and tail-cost curve.

PostgreSQL bridge

Active work

PostgreSQL 18.6 with a second smgr slot compiles, boots, and restarts.

Boundary: page callbacks, WAL barriers, truncate, crash recovery, and economics.

Cell fleet and metacluster

Proposed

Topology separates transaction domains, ranges, objects, cells, and fleet routing.

Boundary: no cross-cell transaction; placement and migration remain future work.

OSS launch

Active work

Repository, RFCs, evals, OTel, research loop, contributor board, and local tracker exist.

Boundary: no remote, license remains proposed, and the repository is unpublished.

[04]Architecture Review 1 decisions

Each row needs an explicit accept, revise, or reject outcome.

DStatusProposed decisionTradeoff
D1ReviewA tenant database is the transaction domain inside one bounded cell; transactions do not cross cells.Preserves useful FDB-like scope while giving up global atomic transactions.
D2ReviewReplicated logs own the unobjectified committed suffix; object storage owns bulk state after fenced publication.Avoids synchronous object publication but requires bounded WAL and objectification lag.
D3ReviewKeep full transaction-system generation replacement as the correct recovery fallback.Simple and auditable, with a larger coordinated event on role loss.
D4ReviewPostgreSQL WAL, LSN, and tuple MVCC remain authoritative in the first bridge.Protects compatibility but does not prove PostgreSQL on native objectKV transactions.
D5ReviewOne commit history remains truth; columnar bases merge a durable tail through T or return unavailable.Exact freshness turns materialization lag into query and retention pressure.
D6ReviewLaunch objectKV as a research kernel before making database replacement or production HTAP claims.Improves credibility and contribution quality while giving up a larger launch narrative.

[05]Stop or narrow conditions

01

Any acknowledged loss, serializability violation, stale-generation commit, premature WAL pop, or incorrect reconstruction.

02

Recovery depends on permanent database bytes rather than retained authority state and the unobjectified suffix.

03

The clean RFC-0055 curve misses its frozen 1.10 threshold, or any unsafe benchmark control passes.

04

GCS request cost, tail latency, throttling, or brownout misses declared ceilings after one tuning pass.

05

The PostgreSQL bridge requires a second commit decision or permits a page ahead of durable PostgreSQL WAL.

06

Exact HTAP requires a second truth, mixes manifests, or needs unbounded analytical-tail retention.

  • Stop addingDistributed roles, metacluster machinery, and broad consumer features until the existing curves decide the design.
  • Stop parallelTreating Redis, search, PostgreSQL, and HTAP as simultaneous launch tracks. They are pressure tests.
  • Stop optimizingBefore the owning metric, negative controls, and comparison envelope are frozen.
  • Stop claimingAhead of GCS, independent-host, PostgreSQL crash, and durable HTAP-source receipts.

[06]Recommended calibration order

  1. Complete the clean resolver hotspot curve.Run every skew and crossing point plus all five controls.
  2. Run the GCS physical and economics gate.Measure request amplification, throttling, tail latency, and brownout in objectKV-dev.
  3. Route real PostgreSQL page callbacks.Execute the WAL, checkpoint, restart, truncate, and crash matrix.
  4. Build the durable HTAP source.Add manifests, snapshot leases, interval tail reads, and the T - Wp cost curve.
  5. Repeat recovery across independent hosts.Test transaction-system recovery and objectification across real failure domains.
  6. Optimize the measured recovery bottleneck.Test compact tLog summaries, checkpoint cadence, and parallel recruitment before adding roles.
