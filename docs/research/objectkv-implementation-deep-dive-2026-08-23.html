01Answer

objectKV is directionally coherent as an open-source research kernel. The strongest evidence is semantic and local. The decisive remaining risks are physical stability and economics, bounded recovery, and composed end-to-end behavior.
Question

Is objectKV becoming a coherent architecture, and what must the next proof cycle establish?

Counter

Narrow the thesis if repeated object authority is unstable, PostgreSQL needs dual commit authority, recovery depends on full DB bytes, or exact HTAP needs an unbounded tail.

Next

Classify MinIO, admit the clean resolver curve, then run GCS physical, PostgreSQL crash, durable HTAP, and independent-host recovery gates.

Confidence

Medium. Broad local contracts, narrow remote and composed receipts.

Claim boundary

Research kernel. Not yet a FoundationDB replacement, distributed PostgreSQL, or ZebraDB.

06Bounds and tradeoffs

The constraints are the architecture. Relaxing them casually converts a bounded kernel into an unbounded distributed system.

D1
Tenant transactions stay inside one cell
Optimize: useful multi-range serializability with bounded failure. Give up: cross-cell atomicity.
D2
tLogs own the recent suffix
Optimize: fast commits without synchronous object publication. Pay: retained-WAL pressure and recovery inventory.
D3
Objects never become coordination
Optimize: tolerate object-store latency and weak primitives. Pay: explicit generation and publication-root authority.
D4
Full-generation recovery stays the fallback
Optimize: auditable fencing and recovery. Pay: larger coordinated recovery events.
D5
Transactions and values stay bounded
Optimize: order, conflict checking, retry, and durable queues. Give up: long compute inside the kernel.
D6
Exact HTAP is base plus tail
Optimize: one fresh logical truth. Pay: lag becomes scan cost and retention pressure.
D7
Invariant aggregates are transactional
Optimize: correct short decisions. Pay: write amplification and projection maintenance.
D8
PostgreSQL WAL is initial authority
Optimize: crash compatibility. Give up: an immediate native-transaction claim.
D9
Formats sit below logical history
Optimize: workload-specific Parquet, Vortex, or row layouts. Pay: explicit format and compaction policy.
D10
Cells bound fleets; ranges scale within cells
Optimize: operational radius without shard-level transaction silos. Pay: explicit placement and migration.

07What comes next to verify

Sequence by falsification value. Do not add more roles or consumer surfaces until these gates decide the current shape.

  1. Classify MinIO authority
    Capture request-level endpoint, backend identity, credentials identity, bucket, prefix, container events, responses, and object lifecycle without changing the suite.
    Exit: deterministic classification and same-suite repeat after one narrow correction.
  2. Admit or reject the clean resolver curve
    Run independent, missed-hot-key, 25% crossing, and 100% crossing profiles with all integrity controls.
    Continue: conservative balanced ratio at least 1.10.
  3. Prove GCS physical behavior and economics
    Freeze bytes, requests, latency, throttling, retry, brownout, exact range, root update, compaction, and cost curves in objectKV-dev.
    Continue: size-independent open and declared cost ceilings.
  4. Put real PostgreSQL pages through the bridge
    Exercise heap, index, extend, truncate, checkpoint, restart, and kill points while PostgreSQL WAL stays authoritative.
    Stop: any dual commit decision, page ahead of WAL, or acknowledged loss.
  5. Turn HTAP overlay into a durable source
    Add versioned manifests, leases, schema history, durable change objects, interval reads, and retention. Measure cost against T - Wp.
    Continue: exact result and work proportional to uncovered tail.
  6. Repeat recovery across independent hosts
    Compare compact summaries, checkpoint cadence, and parallel recruitment while preserving corrupt, stale, missing, and slow-role controls.
    Continue: zero DB scans and at least 10% owning-median improvement.
  7. Compose one bounded cell receipt
    Measure read authority, proxies, resolvers, tLogs, objectification, fresh serving, failure, recovery, and exact reads in one path.
    First valid end-to-end latency, throughput, availability, and cost claim.

08The emerging vision of objectKV

An open-source, object-native, FoundationDB-like transactional kernel built as a fleet of bounded cells, where replicated logs own the recent committed suffix, immutable object storage owns permanent bulk state, and one exact version history feeds transactional and analytical layouts.
01
Cells, not atomic shards
Transactions span ranges inside a tenant database. Cells bound recovery, failure, and operations.
02
Objects, not permanent storage servers
Immutable segments and manifests own bytes. Serving workers can be rebuilt.
03
Small, explicit coordination
Versions, conflicts, order, fencing, and logs stay in the constrained kernel.
04
One history, multiple layouts
MVCC segments, Parquet, Vortex, indexes, and projections share one truth.
05
Evidence is implementation
Claims own metrics, negative controls, budgets, OTel, and immutable receipts.

09Evaluation and auto-research system

The current system has 65 TOML suites and 41 ledger records with hard gates, budgets, negative subjects, OTel telemetry, and artifact receipts. The next gain is richer external-state and composed-cell evidence, not more suite count.

01
Freeze the question before tuning
One primary metric per lane, immutable seeds, declared budgets, and unsafe controls.
02
Candidate code is mutable; evidence contracts are not
The research agent may not move references, runners, suites, or budgets to manufacture a keep.
03
Telemetry must explain the curve
Promote backend identity, response class, tail bytes, topology, checkpoint policy, and role timing to trace dimensions.
04
Every attempt gets a receipt
Keep or discard, exact candidate and parent, suite hash, run IDs, gates, metrics, and artifact references.
