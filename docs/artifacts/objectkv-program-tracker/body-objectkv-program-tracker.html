Current decision

Keep objectKV native-first while the measured envelope holds

The matched-topology candidate passed exact reads, zero-object serving, bounded bytes, telemetry, throughput, and p99 constraints in both process orders. D56 keeps the native resident read path active and retains FoundationDB as a correctness oracle and fallback. It does not admit a distributed transaction cell.

What has changed

The project separates execution, transaction durability, and permanent object state. The R0 mechanism reconstructs a complete resident image from regional GCS plus retained history, survives worker replacement, and performs zero object operations in the measured read window. The matched control now pays for the same recovered topology, authority processes, and owned-value boundary. The next question is whether the native advantage survives concurrency and a working set larger than memory.

Work in progress log

2026-08-27

Matched-topology native GP3.1 passes its envelope

Across 15 samples per subject and order, native retained 90.89% and 91.97% of direct RocksDB throughput. Native p99 was 8.66% and 8.68% lower. All 64 hard-gate evaluations passed, every run appeared in traces, metrics, and logs, and the private GCP environment was fully torn down.

2026-08-27

First unmatched GP3.1 control rejected as a program decision

The earlier candidate retained 84.11% and 82.68% of a bare direct RocksDB control and missed p99 at 1.210x and 1.272x. D56 supersedes the D52 pivot because the control did not pay for the recovered topology, authority processes, and owned-value boundary carried by the native subject.

2026-08-27

GP3.1 throughput enters, p99 fails, read boundary changes

Manifest-bypass improved candidate throughput 11.18%. AB and BA retained 80.68% and 80.02% of direct RocksDB throughput, while p99 remained 1.353x and 1.300x control. The executable p99 gate failed twice, all mechanism and OTel gates passed, and the next subject is an engine-native resident data plane.

2026-08-27

GP3.1 real-infrastructure comparison misses parity

The public SingleRange path passed recovery, generation, cursor, byte-bound, and zero-object-read gates on a named GCP local NVMe device. It reached 516,973 reads/s and 2.482 microseconds p99 versus 702,142 reads/s and 1.749 microseconds for direct RocksDB. GP3.1 stays Evaluating while one bounded optimization cycle targets the 26.37% throughput and 41.91% p99 gaps.

2026-08-26

G4.10b composition clears its local gates

The 25% conflict candidate reached 1,075.343 resolved outcomes/s, 104.274 ms maximum p99, and 28.776x the one-entry control while exact object-plus-suffix recovery, committed and conflicted retry, both leader failovers, voter restart, fresh-client reconstruction, and both unsafe controls passed.

2026-08-26

G4.10 retains the 32-item independent-request commit proxy

The 16-item, 64-caller configuration was discarded on latency. The separately frozen 32-item candidate reached 1,157.369 tx/s and 76.101 ms maximum p99, 6.356x the one-entry control. Sparse, byte, overload, oversized-request, retry, replay, failover, and restart gates passed in their local scope.

2026-08-26

G4.9 transaction batch clears local mechanism gates

Sixteen independent transactions now share one Raft entry and commit version while retaining distinct batch orders and retry outcomes. The release candidate reached 559.511 tx/s and 34.016 ms maximum p99, 3.682x the one-entry control. Duplicate identities and early acknowledgement were rejected.

2026-08-26

G4.8 concurrency mechanism discarded

Bounded one-entry submission preserved correctness and improved throughput 3.964x, but reached only 153.708 tx/s and 264.887 ms maximum p99. Followers grouped appends while the leader remained one append per transaction. RFC-0032 freezes an explicit batch entry as G4.9.

2026-08-26

G4.7 authenticated object frontier completed locally

A pending immutable closure and data-voter quorum certificate protected physical recovery-stream pop. All 16 records were removed, exact object recovery survived both authority failovers and one voter restart, and three unsafe controls were rejected.

2026-08-26

G4.3 process recovery diagnostic completed

A three-process authority selected the object and logical txLog roots. One worker recovered and was killed before reading; a distinct empty-scratch replacement returned exact base, update, delete, and tail-only insert reads. The lazy path reached 6.542 ms p99 and 35,811 object bytes. The local quorum-file tail is diagnostic, so status remains Evaluating.

2026-08-25

Tetris boundary example runs on real primitives

The frozen objectkv-boundary-v0 maps each game input to an MVCC mutation batch and an opaque okv-log envelope. Scripted play exercises commits, snapshot reads, exact replay recovery, and branch-local history in one process without claiming durability.

Next architecture review

The next review starts with one measured question: can coverage checks, overlay lookup, range location, dynamic dispatch, and value copying be reduced enough for the public read path to stay within 20% of direct RocksDB? The comparator must also enforce the p99 ratio directly, and the rerun needs reversed order for drift. If that focused cycle still misses, keep object publication, branching, log, and HTAP leverage above RocksDB or TiKV instead of owning the serving wrapper. RAM, independent-host commit, PostgreSQL, and full Cell v0 integration remain downstream of that decision.
