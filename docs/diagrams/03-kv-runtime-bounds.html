How does a disposable KV Runtime stay finite?

DIAGRAM 3 OF 3

It never attempts to hold the database. It holds a bounded recent mutation tail, a bounded cache of immutable blocks, and only the ranges currently assigned to it.

Pressure response, from cheapest to hardest

Evict immutable blocks

Drop cold RAM and NVMe entries. Re-fetch from object storage on demand.

Freeze and objectify

Move recent committed mutations into an immutable SST, publish the manifest, and release tail memory.

Split or move ranges

Data Distributor assigns hot or numerous ranges to another KV Runtime with spare CPU, RAM, and I/O.

Rate limit

Slow admission when txLog bytes, C minus O, cache churn, or objectification debt crosses the soft envelope.

Refuse new commits

At the hard retained-tail or RPO limit, fail writes predictably. Existing reconstructable reads may continue.

Range is the scaling unitA KV Runtime does not grow forever. The control plane changes its range assignments when CPU, RAM, NVMe, network, scan concurrency, or tail lag approaches a configured limit.
