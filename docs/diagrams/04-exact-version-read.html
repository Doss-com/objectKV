How does one KV Runtime read the database at version T?

DIAGRAM 4

The transaction system chooses one cell version. The KV Runtime proves it has applied through that version, then resolves objectKV-owned MVCC entries inside one shared ordered object LSM.

03

One database read

Point and scan share one physical MVCC ordering.

Point get(key, T)

1Escape the raw binary user key.
2Seek at complemented version T.
3First version less than or equal to T wins.
4A point tombstone returns absent.

Ordered scan(begin, end, T)

1Scan one physical user-key interval.
2Group entries by decoded user key.
3Resolve one visible version per key.
4Stop at the visible-row limit.

04

Physical hierarchy

Fast compute is disposable. Objects remain authoritative.

RAM

Recent committed overlay, decoded blocks, routing and applied-frontier state.

NVMe

Bounded immutable block cache. Delete it and reads become slower, not incorrect.

S3-compatible objects

Immutable SSTs, manifests, checksums, and the rebuild base after txLog replay.

RAM miss -> NVMe miss -> object range GET -> checksum -> cache -> row
Stable key identityRange Engine IDs are not stored in user keys. Split and movement change routing ownership without renaming durable keys.
Measured boundaryAt 256 retained versions, near-latest cold point p99 was 6.69 ms, but a cold scan read 74.0 MB and physical amplification reached 283.47x.
Next required gateRFC-0059 adds a monotonic read floor and version-aware object compaction. Range tombstones, GCS latency, concurrent tail application, and movement remain open.
